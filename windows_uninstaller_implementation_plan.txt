WINDOWS UNINSTALLER / CLEANUP UTILITY
FULL IMPLEMENTATION PLAN
Version: 1.1
Date: 2026-09-21
Scope: Native Windows desktop application inspired by the feature class of Revo Uninstaller Pro / IObit Uninstaller, without Browser Extensions Manager, Software Updater, Software Relocator, Command-Line Interface, Quarantine Instead of Immediate Deletion, or Portable Mode.

======================================================================
0. EXECUTIVE SUMMARY
======================================================================

Goal
----
Build a production-grade Windows application that can discover installed software, perform normal/forced/complete uninstalls, find leftovers, manage startup items/services/tasks, clean junk and privacy history, securely shred selected files, inspect running applications, monitor installations, and provide recovery/audit facilities.

The product should feel like a modern Windows utility rather than a clone of a legacy desktop application.

Core product promise
--------------------
1. Explain what will be changed before changing it.
2. Prefer the software vendor's own uninstaller when available.
3. Use evidence-based leftover detection rather than name-only matching.
4. Never silently treat ambiguous data as safe to delete.
5. Keep normal UI operation unelevated; elevate only for privileged work.
6. Record every destructive operation in an audit log.
7. Make recovery possible through transaction snapshots and Windows System Restore where available.
8. Keep the uninstaller engine deterministic and testable independently from the UI.

- HKLM\\Software\\WOW6432Node\\Microsoft\\Windows\\CurrentVersion\\Uninstall

----------------------------------------

- Internal ApplicationId: stable GUID generated by the app
- External identities: MSI ProductCode, UpgradeCode if available, package family name, uninstall registry key path, executable fingerprint, etc.

Deduplication priority:
1. Exact MSI product code
2. Exact package identity
3. Exact uninstall registry identity
4. Strong combination of publisher + normalized name + version + location
5. Weak heuristic merge only with explicit confidence score

Never merge two records purely because their display names match.

3. PRIVILEGE AND SECURITY MODEL
======================================================================

3.1 Principle
-------------
The UI should run with the user's normal token. High-integrity privileges are acquired only when a feature genuinely requires them.

Final privilege architecture (LOCKED):
- `Remvora.App` runs unelevated.
- `Remvora.Elevation` is a separate executable.
- UAC elevation occurs only when a planned operation contains privileged steps.
- The UI sends typed requests over a named pipe.
- The elevated worker authenticates the caller, validates the request again, applies protected-target rules, executes only supported operations, and returns structured results.
- The worker must not accept arbitrary command strings, arbitrary registry scripts, or arbitrary delete paths from the UI.

3.2 Elevation flow
------------------
1. UI determines that the requested operation needs admin privileges.
2. UI starts Remvora.ElevatedWorker.exe with runas/UAC.
3. Worker creates a named pipe server with a restrictive security descriptor.
4. UI connects using a nonce-bound authenticated session.
5. UI sends one structured operation request.
6. Worker validates the request against an allow-list of operation types.
7. Worker executes the operation.
8. Worker returns structured progress/results.
9. Worker shuts down when no longer needed, unless a short-lived session is batching operations.

3.3 Never trust IPC input
-------------------------
The worker must validate:
- Paths
- Registry hives/paths
- Service names
- Task paths
- MSI product codes
- Package identity
- Operation type
- Item IDs
- Requested file actions

Do not expose a generic "run arbitrary command" IPC method.

3.4 Path safety
---------------
Canonicalize paths before destructive work.
Reject:
- Empty paths
- Relative paths
- Paths with unresolved traversal
- Device paths unless explicitly supported
- Critical OS locations
- The application's own installation directory during self-uninstall unless a controlled self-delete workflow exists

Use a protected-path policy list and a higher-risk list.

Protected examples:
- C:\\Windows
- C:\\Windows\\System32
- C:\\Windows\\WinSxS
- C:\\ProgramData\\Microsoft\\Windows
- Boot/system volumes and critical bootloader paths
- Registry roots and branches known to be system-critical

Protection should be rule-based and explainable, not only string-prefix based.

3.5 Registry safety
-------------------
Before deleting any registry value/key:
- Verify the exact hive/view
- Record original value/type and parent context
- Verify it belongs to the selected application transaction
- Check protected path rules

Do not bulk-search the entire registry and delete every value containing the application name.

6. INSTALLED APP DISCOVERY ENGINE
======================================================================

6.1 Registry discovery
----------------------
Implement a RegistryUninstallSource that enumerates both 32-bit and 64-bit views explicitly.

Metadata to read:
- DisplayName
- DisplayVersion
- Publisher
- InstallDate
- InstallLocation
- EstimatedSize
- UninstallString
- QuietUninstallString
- ModifyPath
- URLInfoAbout
- HelpLink
- Comments
- SystemComponent
- ReleaseType
- ParentKeyName
- NoRemove
- NoModify
- NoRepair

The Windows Installer documentation defines these uninstall registry values, including DisplayName, DisplayVersion, Publisher, InstallLocation, EstimatedSize, and UninstallString.

Do not display hidden/system entries by default when they are clearly marked SystemComponent or equivalent. Offer an advanced filter to expose them.

6.2 MSI discovery
-----------------
Call MsiEnumProductsEx to enumerate installed/advertised products across relevant contexts.

For each product, correlate:
- ProductCode
- Context
- User SID when applicable
- Display metadata
- Installation state

When uninstalling an MSI product, prefer MsiConfigureProductEx for known ProductCode-driven removal rather than trying to modify the MSI registry manually.

6.3 Packaged app discovery
--------------------------
Use PackageManager APIs to enumerate packages for the current user. With appropriate elevation and explicit user selection, support machine/user inventory as permitted by Windows.

Store:
- Package full name
- Package family name
- Display name
- Publisher
- Version
- Install location
- Package type

6.4 Inventory refresh
---------------------
Triggers:
- App startup (light refresh)
- Manual refresh
- After uninstall
- After package deployment/removal
- After installation monitor session ends

Make refresh cancellable.

7. SIZE CALCULATION ENGINE
======================================================================

Implement two concepts:
1. ReportedSize: installer-provided estimate
2. ActualSize: measured files under trusted install/data roots

For actual size:
- Traverse directories asynchronously
- Skip inaccessible folders with a recorded warning
- Respect reparse points to avoid loops
- Avoid following arbitrary mount points/junctions unless explicitly configured
- Cache hashes/metadata only where needed

Do not make uninstall correctness depend on successful size calculation.

======================================================================
8. STANDARD UNINSTALL ENGINE
======================================================================

8.1 Uninstall strategies
------------------------
Create:
IUninstallStrategy

Implementations:
- MsiUninstallStrategy
- RegistryCommandStrategy
- PackageUninstallStrategy
- Custom/UnknownStrategy

Selection rules:
1. If application is a known MSI product -> MSI strategy.
2. If packaged app -> package strategy.
3. Otherwise use validated uninstall command from registry.

8.2 Command validation
----------------------
Parse command line without naïve string splitting.

Capture:
- executable
- arguments
- working directory
- source registry key

Display exact command information in advanced details.

Do not allow an uninstall command to silently become arbitrary file deletion.

8.3 Pre-uninstall checks
------------------------
- Confirm app still exists
- Detect running processes associated with the app
- Detect services
- Detect scheduled tasks
- Detect file locks
- Check free disk space for transaction metadata
- Determine whether a restore point should be attempted

8.4 Restore-point policy
------------------------
For major uninstall operations, try to create a Windows System Restore point when available and permitted by Windows.

Use SRSetRestorePoint through dynamically loaded SrClient.dll as recommended by Microsoft documentation.

Important: System Restore is an additional safety layer, not the only undo mechanism.

8.5 Run vendor uninstaller
--------------------------
Launch using the correct privilege level and wait for process completion where possible.

Handle:
- normal completion
- user cancellation
- reboot required
- timeout
- process crash
- child process handoff

Never assume exit code 0 means every component was removed.

8.6 Post-uninstall refresh
--------------------------
After the vendor uninstaller finishes:
1. Refresh inventory.
2. Re-evaluate running processes.
3. Re-scan candidate leftovers.
4. Present a leftover review screen.

9. COMPLETE UNINSTALL / LEFTOVER SCANNER
======================================================================

9.1 Scanner architecture
------------------------
ILeftoverScanner
  -> FileScanner
  -> DirectoryScanner
  -> RegistryScanner
  -> ServiceScanner
  -> ScheduledTaskScanner
  -> StartupScanner
  -> ShortcutScanner
  -> AppDataScanner
  -> ProgramDataScanner
  -> MetadataScanner

Each scanner returns candidates with evidence and confidence.

9.2 Evidence model
------------------
Strong evidence:
- Exact known install path from uninstall metadata
- Exact MSI product/component identity
- Exact package install directory
- Installation monitor recorded the item as created by the app
- Service binary path points directly into app installation directory
- Scheduled task action points directly into app installation directory

Medium evidence:
- Vendor + normalized application name match in a known data location
- Parent directory clearly belongs to the app
- Startup command points to app executable

Weak evidence:
- Filename merely contains app name
- Generic publisher folder in AppData
- Shared runtime/cache directory
- Registry value mentions app in arbitrary text

Default selection:
- Strong evidence: selected
- Medium evidence: selected only if policy says low risk
- Weak evidence: not selected

9.3 Path families to scan
-------------------------
File system:
- InstallLocation
- ProgramFiles
- ProgramFiles(x86)
- ProgramData
- AppData\\Local
- AppData\\Roaming
- LocalAppDataLow where applicable
- Start Menu program folders
- Desktop shortcuts
- Common application-data roots

Never recursively scan the entire C: drive for ordinary uninstall.

9.4 Registry scanning
---------------------
Potential scopes:
- HKCU\\Software\\<Publisher/App>
- HKLM\\Software\\<Publisher/App>
- 32-bit equivalent views
- App-specific uninstall metadata
- Known update/service registration branches

Avoid unrestricted global substring searches.

9.5 Services
------------
Use Service Control Manager APIs to enumerate services and correlate:
- Service name
- Display name
- BinaryPathName
- Dependencies
- Start type
- Running state
- Associated executable publisher/signature

A service should only be considered an app leftover when there is strong evidence linking it to the target application.

9.6 Scheduled tasks
-------------------
Use Task Scheduler 2.0 interfaces to enumerate tasks and inspect:
- Path
- Author
- Actions
- Triggers
- User/account
- Executable paths

Do not delete Microsoft/system tasks solely because a task contains a vendor name.

9.7 Startup entries
-------------------
Inspect at minimum:
- HKCU Run / RunOnce
- HKLM Run / RunOnce
- Startup folders
- Service startup
- Scheduled-task-at-logon entries

The four primary Run/RunOnce registry keys should be represented explicitly.

9.8 Shortcut cleanup
--------------------
Inspect Start Menu and desktop shortcuts whose targets point to removed application binaries.

Show shortcut target and link path before deletion.

======================================================================
10. CANDIDATE SCORING ENGINE
======================================================================

Use deterministic scoring, not an AI model.

Example score components:
+100 exact install-monitor match
+90 exact install directory match
+80 exact service binary under install directory
+80 exact task action under install directory
+75 exact vendor + app directory match
+50 app-specific registry path
+40 app-specific AppData folder
+30 shortcut target match
-80 protected path
-60 shared runtime indicator
-50 Microsoft-signed/system component
-40 generic cache/temp folder

Map total score to:
SAFE / LIKELY / AMBIGUOUS / PROTECTED

Expose the evidence in the UI:
"Matched because: service binary is C:\\Program Files\\Vendor\\App\\service.exe"

Do not expose raw mathematical score as a fake certainty metric. Present an evidence category plus reasons.

11. FORCED UNINSTALL
======================================================================

11.1 Entry points
-----------------
Allow the user to select:
- Broken installed-app entry
- Executable
- Install directory
- Shortcut

11.2 Discovery workflow
-----------------------
1. Resolve target metadata.
2. Find possible uninstall source.
3. Find running processes.
4. Find services/tasks/startup items.
5. Find installation and data directories.
6. Build candidate set.
7. Present preview.
8. Require explicit confirmation.

11.3 Forced cleanup policy
--------------------------
If the vendor uninstaller cannot run, the app may remove known associated components after explicit confirmation.

Do not infer ownership from filename alone.

11.4 Reboot handling
--------------------
When a file is locked and cannot be removed safely:
- Report it.
- Offer a reboot-required cleanup transaction.
- Use Windows supported mechanisms for pending replacement/deletion where safe.
- Never schedule arbitrary destructive scripts without recording exactly what will execute.

12. INSTALLATION MONITOR
======================================================================

Goal
----
Record what an installer changes so future uninstallation can rely on direct evidence instead of heuristics.

12.1 Session lifecycle
----------------------
Start Monitor
-> baseline capture
-> launch installer
-> user installs normally
-> stop monitor
-> post-snapshot
-> diff
-> store installation log

12.2 Baseline capture
---------------------
Capture:
- Relevant file tree metadata under monitored roots
- Registry trees under chosen install-related hives
- Services inventory
- Scheduled tasks inventory
- Startup entries
- Packaged app inventory

Do not snapshot the entire Windows registry or entire disk.

12.3 Change capture methods
---------------------------
MVP:
- Before/after snapshots
- ReadDirectoryChangesW for selected live directory monitoring
- RegNotifyChangeKeyValue for selected registry trees
- Service/task inventory diff before/after

Advanced later:
- ETW-based process/registry/file correlation if measurement proves snapshot monitoring insufficient.

12.4 Installer process tracking
-------------------------------
Track the launched installer process tree where possible.

Store:
- PID
- Parent PID
- Executable path
- command line
- start/exit timestamps

The monitor should know which installer process initiated the installation, but should not assume every child process is part of the product.

12.5 Noise filtering
--------------------
Ignore or downgrade common noise:
- Windows Defender updates
- Windows Search/indexing activity
- Explorer thumbnail/cache updates
- system-wide temporary files
- unrelated background processes

Make the noise rules configurable and testable.

12.6 Installation log view
--------------------------
Show:
- Created files
- Modified files
- Created registry keys
- Modified registry values
- Services created/changed
- Tasks created/changed
- Startup entries created
- Summary counts

Export to JSON/text for diagnostics even though the product has no CLI requirement.

Recommended default behavior:
1. Process one application at a time.
2. Let each vendor uninstaller finish before continuing.
3. After each uninstaller, scan leftovers.
4. Ask once per app unless the batch was explicitly configured as unattended within the UI.

Do not run multiple uninstallers concurrently.

Failure modes:
- unavailable uninstall source
- reboot required
- process still running
- permission denied
- uninstall timeout
- user cancelled

Batch UI should preserve per-application result status.

18. SECURE FILE SHREDDER
======================================================================

Purpose
-------
Provide deliberate permanent deletion for user-selected files/folders.

Scope separation
----------------
Shredder must be a separate tool. Never invoke it automatically from uninstall cleanup.

Implementation
--------------
Modern storage hardware, filesystems, SSD wear-leveling, compression, encryption, and copy-on-write behavior mean software overwrite passes cannot guarantee physical media destruction.

Therefore UI language should be:
"Attempts to make deleted file contents difficult to recover"
rather than
"guaranteed irreversible destruction."

Recommended behavior:
- default safe deletion using documented Windows deletion semantics
- optional overwrite pass for user-selected files on supported filesystems
- explicit warning about SSD/flash limitations
- final confirmation showing exact paths

- Low-use

======================================================================
20. BACKUP / UNDO / TRANSACTION ENGINE
======================================================================

20.1 Core idea
--------------
Before a destructive cleanup, create a transaction describing every intended change.

Transaction phases:
PREPARING
PREVIEWED
AUTHORIZED
APPLYING
VERIFYING
COMPLETED
PARTIAL_FAILURE
ROLLED_BACK
ROLLBACK_PARTIAL

20.2 File backup
----------------
Because the requested scope excludes a quarantine system, use a transaction backup only where needed for undo semantics.

Recommended approach:
- For files that are small and safe to capture, copy them into a transaction backup directory.
- For large trees, store metadata + use Windows System Restore where appropriate; do not duplicate multi-gigabyte application directories unless explicitly required by the transaction type.
- Never leave backup copies indistinguishable from ordinary user files.

20.3 Registry backup
--------------------
Record exact original values and key existence state.

For larger system-state recovery, rely on Windows System Restore / supported Windows mechanisms rather than pretending that a handful of exported .reg files are a full system backup.

Microsoft notes that system-state applications should use Volume Shadow Copy Service rather than RegSaveKey/RegLoadKey alone for full system state backup/restore.

20.4 Service/task rollback
--------------------------
Store:
- original configuration
- original enabled/start mode
- binary path
- account
- description
- dependencies
- task XML where accessible

Rollback should recreate prior configuration only when safe and supported.

20.5 Undo workflow
------------------
History -> select completed transaction -> Review undo -> Apply -> Verify

Not every vendor uninstaller action can be perfectly reversed. The UI must mark transactions as:
- Fully reversible
- Partially reversible
- Requires System Restore for broad rollback

Never claim "undo" when only a subset of changes is recoverable.

39. SECURITY / THREAT MODEL
======================================================================

Threats
-------
1. Malicious local process attempts to send commands to elevated worker.
2. TOCTOU: file changes between scan and deletion.
3. Malicious reparse point redirects deletion.
4. Untrusted executable is launched from an uninstall entry.
5. Compromised installer attempts to abuse monitor privileges.
6. Logs expose secrets.
7. Corrupted transaction data causes unintended rollback.

Mitigations
-----------
- restrictive named-pipe ACL
- request validation and allow-list
- re-resolve/revalidate paths immediately before destructive operation
- no reparse-point traversal
- signed application binaries
- verify executable paths and signatures for display; do not overtrust them
- transaction integrity checks
- structured serialization with versioning
- audit logging
- least privilege
- explicit confirmation of destructive actions
